## 1. 结论

已完成“启动后先自动居中，再跟随移动方块”的实机验证。红块只需**唯一且位于相机画面内**，无需预先摆在画面中心。Action 先进入 `INITIAL_CENTERING`，首次达到中心半宽 12 px、半高 9 px 并连续稳定 3 帧后进入 `CENTER_HOLD`；红块移出正常退出区后转为 `TRACKING`，回到中心区后继续保持。2026-09-22 后续优化增加极短检测闪断过渡；持续无效时进入 `LOST_HOLD` 并输出零速度。

快档把速度指令上限由 0.005 提到 **0.015 m/s（15 mm/s，3 倍）**，XY 比例增益由 0.080 提到 0.240，加速度上限由 0.030 提到 0.090 m/s²。快档通过四个基坐标方向短脉冲和 90 秒连续 Action。两次不同起点的现场记录中，首次居中图像误差收敛速度由 2.06 提到 **5.59 px/s，约 2.7 倍**；这不是机械臂 TCP 速度的精确三倍标定。

### 2026-09-22 连贯性优化（待实机复测）

现场反馈连续运动呈约 0.20 s 一步的跳动。原配置中 MoveIt Servo 以 5 Hz 发布单点关节位置轨迹，90 秒实机记录收到 457 条 Servo 状态消息，约 5.1 Hz。关节轨迹控制器对只有位置的轨迹采用线性插值，目标每轮更新时关节指令的斜率会改变。先把 Servo 周期改为已通过短脉冲方向验证的 **0.10 s（10 Hz）**，并把本报告后续测试命令的加速度从 0.090 降为 **0.030 m/s²**；15 mm/s 速度上限保持不变。这样可以减小每步目标增量并放缓起停，但已知 0.10 s 周期的实际位移较少。该组合的连续实机跟踪效果尚未验证。

### 可选高速档（待实机逐级验证）

用户希望方块移动更快时机械臂也能更快跟上，所举“5/s、10/s”是相对速度的例子，没有指定物理单位。为了减少拖尾，代码现在允许显式设置最高 **0.075 m/s** 的 Twist 输入上限，即已验证 0.015 m/s 的 5 倍；默认低速值不变。高速档同时用 `gain_mps:=1.200`，让同一像素误差对应 5 倍速度请求，加速度上限仍为 `0.090 m/s²`，保留较缓的爬升。**输入提高 5 倍不代表 TCP 实际速度提高 5 倍**：此前 0.20 s、15 mm/s 短脉冲的 TCP 峰值约 5–7.5 mm/s，停止指令后继续位移约 0.9–1.2 mm；0.10 s Servo 周期的兑现率更低。高速档的实测速度与停车距离尚无证据。

最近一次 90 s 复测（`evidence/stage5/fast15_retest_20260922_152618.json`）中，1829 条非零指令的速度中位数约 14.9 mm/s，已接近旧上限 15 mm/s；因此继续提高速度请求有实际需求。同一记录有 312 条 `LOST_HOLD` 状态，主要来自稳定样本重采集和红目标不唯一；这些时间段保持零速度，也会造成肉眼可见的拖尾。复测没有完整 TCP 轨迹，不能从旧日志推断末端速度提高的倍数。Servo 配置使用 `speed_units`，Twist 值按 m/s 输入；配置里的 `scale.linear` 不负责放大此模式的指令。

在任何高速 Action 之前，先确保旧 Action 已结束、控制状态为手动待命，且场景中的桌面碰撞物、夹爪状态与实物一致。按 `0.030 → 0.045 → 0.060 → 0.075 m/s` 逐级做 x+/x-/y+/y- 短脉冲，逐次检查 JSON 的 `outcome: passed`、运动方向、位移、Servo 状态与控制权释放；任一项异常即停止升级。每次只运行一条命令，例如：

```bash
python3 tools/stage4_direction_pulse.py x+ --operator-ready \
  --high-speed-validation --speed-mps 0.030 --duration-s 0.20 \
  --output evidence/stage4/fast30_x_plus.json
```

逐级方向和停止测试通过后，才把终端 3 的启动参数改为 `servo_publish_period:=0.10 max_speed_mps:=0.075 gain_mps:=1.200 max_acceleration_mps2:=0.090`，先发送短时 Action 并记录 TCP 实测速度、停止后位移和图像误差。`tools/stage5_track_acceptance.py` 现在把带时间戳的 TCP 坐标写入 `tcp_positions`，`tools/stage5_summarize.py` 输出约 100 ms 时间窗内 XY 速度的 P90 和最大值；先比较这些实测值，再判断拖尾是否改善。旧日志只有 TCP 到起点的径向距离，不能据此计算真实轨迹速度。当前报告第 4 节的 15 mm/s 命令仍是已测速度范围内的基准。

### 0.04 m/s 现场复测后的修正（已复测，仍有明显机械抖动）

`fast15_retest_20260922_155914.json` 在 1.92 s 因 `target_not_found` 结束，`fast15_retest_20260922_160000.json` 在 27.91 s 因 `target_not_unique` 结束；这是旧版 `lost_timeout_s=1.0` 的结果，不是 0.04 m/s 的速度限制。在后一段约 28 s 的日志里，非零指令到零指令跳变 22 次，主要由检测瞬断触发；TCP XY 速度的 100 ms 窗口 P90 约 7.5 mm/s、最大约 18.2 mm/s。当前运行命令查到 `servo_publish_period:=0.20 max_speed_mps:=0.04 gain_mps:=0.240 max_acceleration_mps2:=0.090`，所以 0.10 s 平滑周期尚未在这轮应用。

修正后，单次短暂的目标缺失、不唯一或重新收集稳定样本，可在**距最后有效图像最多 0.16 s、名义继续行程最多 5 mm** 的双重约束内沿用上一条指令。连续异常、图像流过期、目标中心突跳、主动取消、TF/碰撞/控制故障仍停止输出。感知连续性允许已锁定目标跳过一次坏帧，但第二次坏帧或超过 0.25 s 的图像间隔会重新采集。目标持续丢失时默认在零速度 `LOST_HOLD` 等待，直到恢复、取消或本次 Action 达到 `max_duration_s`；如需原先的失败超时，可显式设置 `lost_timeout_s>0`。证据工具现在记录 `perception_status`，便于区分色块消失、多候选、中心突跳和图像过期。

已按 `servo_publish_period:=0.10 gain_mps:=0.480 max_acceleration_mps2:=0.090` 复测。操作员确认**真实机械臂比此前更明显地一顿一顿**。这说明仅消除感知瞬断或缩短发布周期不足以解决连续运动抖动。

### 2026-09-22 抖动原因复核与插值改动（待低速实机验证）

180 s 复测证据：`evidence/stage5/fast15_retest_20260922_161513.json`。Action 正常到时结束，Servo 状态全为 0；感知状态中 2105 条是 `stable_target`，仅 3 条 `image_stream_stale` 和 1 条 `collecting_stable_samples`。前 4–8 s 首次居中阶段，XY 指令持续接近 0.040 m/s，没有换向或归零，但 TCP 每 100 ms 窗口速度中位数约 0.0087 m/s、P90 约 0.0113 m/s。结合现场肉眼观察，本轮连续运动的抖动**不能主要归因于目标瞬断**；实际限速/滞后和下游关节轨迹执行方式仍需实机区分。

原链路中 MoveIt Servo 每 0.10 s 输出一个**只有位置**的关节轨迹点。Humble `joint_trajectory_controller` 对这种输入使用线性插值：位置连续，但每次替换轨迹时速度斜率可突变。现把 SDK 实时状态包中的 `actual_qd`（deg/s）换算为 rad/s，作为六关节 velocity 状态；轨迹控制器读取 position+velocity 状态，Servo 输出 position+velocity 轨迹点。这样控制器可用三次插值，使每段内部速度连续，并利用实测关节速度减轻轨迹替换边界的速度跳变；反复替换轨迹时仍需实机验证。此改动保持 ServoJ 的位置命令方式和 8 ms 硬件控制周期。

离线验证：`fairino_hardware` 编译通过，12 个硬件接口测试通过（含 90 deg/s → π/2 rad/s 及无效速度反馈拒绝），真实/模拟两种 xacro 均展开为六关节 position+velocity 状态。**尚未在真实机械臂上验证抖动是否改善，也没有证据表明实际跟随速度提高五倍。** 这次修改涉及硬件接口、共享轨迹控制器和 Servo 配置，须在当前 Action 结束后重启**终端 1 的完整基础栈及终端 3**才能生效；仅重启追踪 Action 不够。重启后先检查 `/joint_states` 的关节速度为有限、合理值，`fairino3mt_execution_controller` 能正常激活，再从 0.005 m/s 上限的短时 Action 开始，之后逐级上调。新证据脚本会以最高 20 Hz 在 `joint_states` 字段记录关节位置和速度，便于对照 TCP 位移和指令。任何实机仍抖动的情况应停止继续提速。

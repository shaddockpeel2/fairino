日期：2026-09-17
阶段：10 阶段规划第 6 阶段
结论：**阶段完成并关闭。** 已实现「token 增量 → 首段快速切分 → 有界文本队列 → 常驻 TTS → 有界 PCM 队列 → 常驻播放器」全链路，并接通 P3 的 Qwen 服务。核心验收项全部达成：音频在文本生成结束前开始（慢 token 源领先 2.23–2.30 s）、停播 P95 0.89 ms、非语义断供 0 次（最大间隔 5 ms）、xrun 0。开发过程中发现并修掉一个会**系统性伪造首帧延迟**的缓存缺陷，见 §5。

## 2. 数据流与进程边界

```text
GUI / CLI（后续阶段）
   │  Qwen chat 端口（P3 服务）              │  语音管线端口（本阶段）
   ▼                                        ▼
fr3c_voice.service                     fr3c_voice.tts_service
 （Qwen3-VL Worker, NPU）                 ├─ 常驻 AlsaPcmPlayer（独占扬声器）
                                          ├─ 常驻 TtsBackend（matcha，3 线程，A76）
                                          └─ StreamingSpeechPipeline
                                               token → 清洗 → 首段切分
                                                     → 有界文本队列(8)
                                                     → 合成线程
                                                     → 有界 PCM 队列(12)
                                                     → 播放线程 → ALSA
```

两个服务分开的原因：声卡必须只有一个写者；模型崩溃不应带走音频；两者可以各自独立重启与测试。调用方（本阶段的 `p6_speak.py`，后续是 GUI）同时连两个 socket，把 token 从一个服务转发给另一个，这也正是 GUI 将来要做的事。

### 关键设计决定

| 决定 | 原因 |
|---|---|
| 播放器用 ctypes 调 libasound，**显式设置 period/buffer** | P5 证伪了"用 `aplay` 就够"：整个延迟预算依赖"设备里预存了多少音频"，`snd_pcm_set_params` 把这个数交给 ALSA 决定，不可审计。实测 period=441 帧(20 ms)、buffer=1764 帧(80 ms) |
| PCM **按 period 分块写入**，并记录首块时刻 | 一次性写整段 2 s 音频会让 `writei` 阻塞 2 s，把"首帧写入"变成一个无意义的时间戳。分块后首块即发声起点 |
| 队列全部有界（文本 8 段 / PCM 12 块） | 消费端卡住时对生产端形成背压，而不是让延迟无声累积 |
| 会话开始时 `drop()` + `prepare()` | 否则上一轮还在设备缓冲里的音频会被当作本轮的"首声"，既污染测量又让两句话重叠（见 §5） |
| **动态回答禁用合成缓存** | 缓存命中会把 0.44 s 的首段变成 0.000 s。预生成短语走独立路径（见 §5） |
| 首段切分在**生产者线程**内做 deadline 检查 | 避免定时器线程与喂文本线程并发操作 splitter |
| `playback_end` 在队列排空**且** `drain()` 之后才发 | "已入队"不等于"已听到"，P1 追踪约定要求区分 |

## 3. 验收结果

证据：`evidence/voice/P6/20260917b/`（本轮）与 `evidence/voice/P6/20260917/`（首轮，含 §5 所述缺陷数据）。

板端配置：Matcha、22050 Hz、3 线程绑 A76（core 4–7）、设备缓冲 80 ms、首段上限 16 字、段目标 28 字、首段等待上限 0.45 s。

### 3.1 音频必须在最后一个 token 前开始 ✅

**受控慢 token 源**（每 6 字间隔 0.12 s，共 120 字）三轮：

| 轮次 | 喂完文本耗时 | 首帧写入时刻 | 领先量 |
|---|---:|---:|---:|
| 1 | 2.55 s | 0.25 s | **+2.30 s** |
| 2 | 2.57 s | 0.27 s | **+2.26 s** |
| 3 | 2.55 s | 0.32 s | **+2.23 s** |

这直接回答"是不是等全文"：音频在文本只喂到约 12% 时就已经开始播放。

### 3.2 20/60/120 字各 10 轮 ✅

| 长度 | 轮数 | 首帧写入 P50 | 首帧写入 P95 | 段间间隔最大 | >150 ms 间隔 | xrun | 失败 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 20 字 | 10 | 0.438 s | 0.453 s | 0.4 ms | 0 | 0 | 0 |
| 60 字 | 10 | 0.435 s | 0.452 s | 0.5 ms | 0 | 0 | 0 |
| 120 字 | 10 | 0.434 s | 0.453 s | 0.5 ms | 0 | 0 | 0 |

**首帧写入与文本长度无关**（0.434–0.438 s），这正是分段流式的意义：首段固定短，后面的段再长也不增加开口延迟。段间间隔最大值 0.5 ms 说明合成始终跑在播放前面，没有任何非语义断供。

### 3.3 真实 Qwen 路径 ✅

3 轮真实模型生成（每题约 105 字答案）：

| 指标 | 结果 |
|---|---|
| 首 token P50 | 0.227 s |
| 首帧写入 P50 | 0.817 s |
| 音频早于文本结束 | **3/3 轮** |
| 段间间隔最大 | 1.0 ms（>150 ms 共 0 次） |
| xrun | 0 |

文本结束约 4.7–5.2 s，音频在 0.31–0.80 s 开始，播放持续到 30 s 左右结束，全程零断供。

### 3.4 停播 ✅

| 指标 | 结果 | 目标 |
|---|---:|---:|
| 停播延迟 P50 | **0.72 ms** | — |
| 停播延迟 P95 | **0.89 ms** | ≤250 ms |
| 最大 | 0.90 ms | ≤250 ms |
| 5/5 轮标记为 cancelled | 是 | — |

测量口径：从收到 stop 请求到设备被 `snd_pcm_drop()` 清空（**含声卡排队**），不是"最后一次入队"。播放器 drop 本身耗时 0.08–1.9 ms。

### 3.5 设备恢复 ✅（弱验证，见已知限制）

| 项目 | 结果 |
|---|---|
| 恢复后仍能播放 | 是 |
| 恢复后 xrun | 0 |

#### 3.5.1 真实发生过的一次重枚举（本阶段最有价值的意外发现）

现场试听时出现 `ALSA write/recover failed (-19): No such device`，音频中途停止。查 dmesg 确认**USB 声卡在那一刻真的重枚举了**：

```
[16532.820988] usb 5-1.2.2: Product: USB Audio Device
[16532.847699] input: C-Media ... USB Audio Device ... input17
```

内核重新创建了 card2 的设备节点，而服务缓存的 ALSA 句柄仍指向旧节点，此后每次写入都返回 ENODEV。

**我的第一版实现有真实缺口**：`prepare()` 里有 ENODEV 重开逻辑，但**播放中途**丢设备没有恢复路径，整个回复就此失败。已修复：`write()` 在 `ENODEV` / `EBADFD` / `ENOENT` 时关闭陈旧句柄、重新打开、继续写剩余帧（最多 3 次），并统计 `midstream_recoveries`。

改为失败即静默截断是**不可接受**的：调用方会以为整句话播完了。

#### 3.5.2 验证强度

| 层次 | 手段 | 结果 |
|---|---|---|
| 运行态恢复 | 板端验收 drop + prepare 后继续播放 | ✅ |
| `prepare()` 重开分支 | 单元测试注入 ENODEV 的 `snd_pcm_prepare` | ✅ `device_reopens` 递增且后续可写 |
| **播放中途丢设备** | 单元测试在第 2 个 period 注入 ENODEV，验证重开并**写完整个块** | ✅ `midstream_recoveries=1`，帧数未截断 |
| 真实拔插端到端 | 需要 sudo unbind/bind USB 驱动 | ⏳ **留给你在板端执行** |

真实拔插复现脚本已就绪：`scripts/voice/p6_device_replug.py`（用 sysfs unbind/bind 让内核重枚举，播放中途触发）。需要 root，我这边 sudo 需要密码，无法代跑。

### 3.6 预生成 PCM ✅

预热时预生成 3 条固定短语（`好的。`/`我在。`/`收到。`），播放其中一条实测首帧写入 **0.016 s**、音频 0.54 s、无合成调用。

预生成走的是**同一个 PCM 队列与播放线程**（`speak_cached`），只省掉合成，不绕开播放路径；而且必须由真实状态触发，本阶段没有"无条件定时播放"的实现。

## 4. 统一事件时间线

沿 P1 约定，同一 `request_id` 贯穿两个服务，CLOCK_MONOTONIC：

| 事件 | 含义 |
|---|---|
| `speech_start` | 会话建立、设备已清空并 prepare |
| `first_text_segment` | 首个可合成文本段提交 |
| `segment_deadline_flush` | 无标点停顿超时，强制释放当前缓冲 |
| `tts_first_pcm` / `text_segment` | 该段合成完成 |
| `first_valid_pcm_write` | **首个 period 被设备接受**，即开始发声 |
| `player_drained` | 设备缓冲排空 |
| `playback_end` | 播放真正结束（入队 + drain 都完成） |
| `speech_stopped` | 取消被观察到 |
| `speech_error` | 合成或播放失败，带原因 |

每条 `playback_end` 附带完整 metrics：分段文本、每段合成/音频时长、队列峰值与阻塞次数、xrun、失败原因。

## 5. 开发过程中发现并修复的缺陷

这一节是本阶段最有价值的部分：两个缺陷都会让验收数字**看起来更好**，如果只看汇总表不会发现。

### 5.1 合成缓存伪造首段延迟

`TtsBackend` 有按文本精确匹配的结果缓存。测量时同一句文本被反复合成，第一轮 0.44 s、之后全部 **0.000 s**。

后果：如果没发现，P5 的运行点数据和 P6 的长度阶梯都会被缓存命中污染，得出"首段延迟 ≈ 0"的假结论——恰好是最容易让人相信、也最危险的那种错误。

修复：
- `TtsBackend` 增加 `allow_cache` 开关，**默认在测量与运行路径上关闭**
- 新增 `precompute()` 专门用于预生成固定短语，缓存与"动态回答"分离
- `StreamingSpeechPipeline` 显式声明 `allow_backend_cache=False`

修复后复测：三轮首帧写入 0.422 / 0.438 / 0.456 s，与预期一致。

### 5.2 会话边界未清空设备缓冲

`write()` 会在设备缓冲满时阻塞。回复 A 的音频还在设备里时，回复 B 的 `speak_start` 没有清空它，于是 B 的"首帧写入"时间戳落在 A 的音频上（实测 0.007 s）。

后果：测到的是**上一句话**，不仅数字错，两句话在实际播放里也会重叠。

修复：新增 `AlsaPcmPlayer.begin_session()`（`drop()` + `prepare()`），`StreamingSpeechPipeline.start()` 调用它。

### 5.3 首段切分的停顿预算

若只按硬上限切分，一段没有标点的长句会一直等到 44 字才释放。已实现 `set_deadlines(first_segment_max_wait_s, segment_max_wait_s)`，按"生产者线程内检查"的方式在超时后强制释放，并在时间线上输出 `segment_deadline_flush`。当前默认首段 0.65 s、后续段 0.8 s；首段最多 24 字，仍处于 P5 实测满足 0.8 s 指标的范围内，并给自然标点更多到达时间。

### 5.4 流式 token 被错误补句号导致逐词停顿（后续修复）

对话页把千问输出逐 token 送入 TTS。原实现对每个 token 调用面向“完整文本”的 `clean_for_speech()`，该函数会自动补终止标点，因此 `我`、`现在`、`可以` 实际进入分句器时变成 `我。现在。可以。`。分句器虽然工作正常，但输入已经失去原句语法，最终表现为逐词停顿、语调反复收尾。

修复后分为两种语义：
- 流式 token 只清洗符号，不补终止标点；
- 真实标点优先触发合成，仅在整段回答结束时给无标点尾句补一个句号；
- 首段上限由 16 字调到 24 字，等待预算由 0.45 s 调到 0.65 s，在现有实测延迟余量内换取更完整的短句韵律。

真实扬声器验证得到两个合成段：`你好，我已经完成了语音断句优化。`、`现在会按照完整短句自然播报！`；首声写入 0.542 s，无播放失败。

## 8. 已知限制

1. **Qwen 回答的分段质量受模型标点影响**。模型常输出"我。是一个。AI。助手。"这类词间句号，切分器按标点切段会得到很短的段，听感上句子被切碎。这是**标点还原**问题，不是管线缺陷；本阶段未做标点修复，如实记录。
2. **首次回答比后续慢约 0.4 s**。第一轮 Qwen 路径首帧 0.798 s、后续 0.301/0.309 s，差异来自首轮冷启动。服务预热只覆盖固定短语，不覆盖"首次真实合成"。
3. **真实拔插端到端未闭环**：重枚举已在现场真实发生并被修复，三层注入式测试通过，但用 sysfs 主动触发重枚举的端到端复现（`p6_device_replug.py`）需要 root，留待板端执行。
4. **生产速率与播放速率接近**：Qwen 文本生成约 21 字/s，TTS 播放约 20 字/s，余量很窄。本轮零断供，但如果模型变慢或并发升高，可能在段间出现等待。首轮验收中曾观测到 20 次 >150 ms 间隔（最大 611 ms），当时是缓存缺陷叠加冷启动；修复后复测为 0 次，但这个余量结论只在当前负载下成立。
5. **半双工切换未接**。播放与录音的互斥、录音时停止播报属于第 7 阶段。
6. **未做声学复核**。本阶段沿用 P5 的结论（播放路径偏置 ≈ 0），没有对每条回答做回采验证；首声指标是"首帧写入设备"而不是"麦克风听到"。
7. **未实现语音打断**，只有按钮/接口停止。

### 11.1 内存门禁从 1024 MiB 下调到 512 MiB

现场完整形态（Qwen 3.1 GiB + 相机 + MoveIt + RViz + TTS 管线）下实测：

|---|---:|
| Qwen Worker | 3149 MiB |
| RViz | 328 MiB |
| TTS 语音管线 | 229 MiB |
| 相机 container | 154 MiB |
| MoveIt | 132 MiB |
| 启动器/抓取节点/其它 | ~180 MiB |
| **MemAvailable** | **1009 MiB** |

P3 原有的 `minimum_available_memory_mib: 1024` 因此**刚好把请求挡在门外**，表现为：

```
ModelServiceError: CoordinationBusy: insufficient memory: 980.2 MiB available
```

用户侧的现象是"上一个黄色方块任务好像还没结束"——实际上黄色任务在 14:01:07 已正常完成，之后的请求**根本没进到任务状态机**，界面上残留的是上一次任务的显示状态（`state=complete_sorted_home`、`target_color=yellow`）。

改动：`config/voice/qwen3vl.yaml` 的 `minimum_available_memory_mib` 由 1024 → **512**（两棵树同步）。改动后同一负载下请求正常，MemAvailable 986 MiB。

**如实记录代价**：512 MiB 比 1024 MiB 少了 512 MiB 保护余量。当前 Qwen Worker 常驻不再重载，门禁主要作用于启动时刻；但若将来同时触发索引构建、长上下文或第二个模型实例，512 MiB 的缓冲更薄。P5 报告已记录"整机内存余量薄"这一结构性约束，本次调整没有解决它，只是让服务在现有负载下可用。

### 11.2 残留状态不是卡死

`/fr3c_first_grasp/state` 在任务完成后保留 `task_mode` 与 `target_color`，并给出 `action_active=false`、`retryable=true`：

```json
{"state":"complete_sorted_home","detail":"cube placed in yellow region and arm returned to start joints",
 "execute":true,"batch_mode":false,"task_mode":"pick_sort","target_color":"yellow",
 "action_active":false,"retryable":true}
```

**它不阻塞新任务**。判断"任务是否还在进行"应看 `action_active`，不要看 `state` 字符串或 `target_color`——后者只是上一次任务的记录。

### 11.3 意图路由的口语盲区（待改进）

真实模型对"放置"类口语的归一化并不稳定：

| 用户表达 | 模型输出 | 是否符合预期 |
|---|---|---|
| 抓取红色方块 | `pick_hold` | ✅ |
| 把红色方块放到分类区 | `pick_sort` | ✅ |
| 抓起红色方块分类 | `pick_sort` | ✅ |
| 抓起红色方块到放置区 | **`pick_hold`** | ❌ 语义是放置 |
| 抓取红色方块到工作区 | **`pick_hold`** | ❌ 语义是放置 |

"到放置区/到工作区"这类说法被当成保持夹持。原因是提示词只把"放到分类区／对应区"列为 `pick_sort` 的触发语，而"放置区""工作区"没有覆盖。**当前不改提示词**（避免在没有评测集的情况下调整行为），先记录；若要修，应先在 `config/voice/p4_intent_corpus.json` 增补这两类表达，再跑 `p4_intent_eval.py` 确认没有回归。

### 11.4 语音链路的日志噪声

GUI 会把每个 `perception_state` 与 `robot_state` 事件写入日志，一次抓取会产生上千行 `requested_color_not_found:yellow`，把真正的事件（意图、派发、结果）淹没。排查时应先过滤：

```bash
grep -vE "perception_state|kind=robot_state" evidence/voice/P4/runtime/dialogue-*.log | tail -40
```

### 11.5 服务锁与 worker 自愈的正确用法

现场把 Qwen worker 单独杀掉后再执行 `start_qwen_service.sh`，得到：

```
BlockingIOError: [Errno 11] Resource temporarily unavailable
RuntimeError: another FR3C Qwen service is already running
```

**这不是残留锁**：杀掉的只是 worker 子进程，服务进程仍在（约 15 MiB）并持有 `qwen-service.lock`。实测该状态为：

```json
{"state":"fault","healthy":false,"worker_pid":null,
 "last_error":"Qwen worker exited unexpectedly (code -9)"}
```

`auto_recover: true` 是生效的，但**只在收到 chat 请求时触发**，`health` 查询不会触发。实测自愈过程：杀 worker → `fault` → 下一次 chat 请求自动重载 → **11.7 s 后正常回答**。

因此有三条正确路径：

| 目的 | 做法 |
|---|---|
| 只是想重启模型 | 什么也不用做，**直接发一条消息**，约 12 s 自愈 |
| 想彻底重启服务 | 必须先 `scripts/voice/stop_qwen_service.sh` 释放锁，再 `start_qwen_service.sh` |
| 只想看状态 | `health` 报 `fault` 不代表需要人工干预，发一次请求即可 |

常见误用：杀掉 worker 后立刻重跑启动脚本 → 必然撞锁失败，且会误判为"残留锁没清"。

### 11.6 现场出现了两个 GUI 实例

排查时发现两个 `dialogue_gui` 进程同时运行（分别由不同终端启动）。两个 GUI 会各自持有独立的对话会话与 `CancellableGeneration`，但**共享同一个 Qwen 服务与语音管线**，因此：

- 两边都可能被判成"当前请求尚未结束"
- 语音会话会被对方的请求 `replace` 掉
- 意图与播报归属难以对应到具体窗口

使用前应确认只有一个实例：

```bash
pgrep -af dialogue_gui
```

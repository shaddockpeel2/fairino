Date: 2026-09-17

       pick_hold, pick_sort and pick_place semantics were NOT changed.

What was added
--------------
A fourth single-shot Action, /fr3c_first_grasp/pick_stack, that grasps the cube
of `color`, rotates it to match the top-face yaw of the cube of `support_color`,
places it on that cube's measured top face, releases it and returns home.

The goal carries the new field `support_color`; the result carries it back plus
two new error codes:
  INVALID_SUPPORT_COLOR=15    goal or configuration rejected before any motion
  STACK_GEOMETRY_REJECTED=16  the requested pair cannot form a two-cube stack

Perception layer change
-----------------------
`is_tabletop_cube` rejected every cube that was not exactly one cube height above
the plane, so the upper cube of a finished stack was invisible and the lower cube
of a new stack could be mistaken for a free table position. Added
`tabletop_cube_tier`, which returns 0 for a cube resting on the work plane and 1
for a cube whose bottom rests on another cube:
  src/fr3c_camera/config/blue_cube_localizer.yaml
    stacking_cube_height_offsets_m: [0.030]
    stacking_tier_tolerance_m: 0.012
`is_tabletop_cube` is now a thin wrapper over it, so the pre-stack colour filter
behaviour is unchanged. The perception status `detected_targets` entries gained
`top_z_base_m`, `grasp_axis_yaw_base_rad`, `grasp_axis_yaw_period_rad`,
`observed_short_long_m`, `object_class`, `nominal_object_size_m` and
`stack_tier`, because pick_stack needs the lower cube's pose and yaw, which the
single-colour filter never selects.

Precision fix found while testing: a cube resting exactly on the plane measured a
gap of about -1.2e-9 m after the frame conversion and was rejected by the
`gap >= 0.0` bound. The lower bound now carries a 1e-6 m tolerance while the
upper bound, which separates one tier from the next, stays strict.

Rotation arithmetic
-------------------
Square top faces make four grasp yaws physically equivalent. The placement
rotation is
  theta = wrap(destination_yaw - target_yaw_offset - source_grasp_yaw, 90 deg)
where wrap takes the nearest whole 90 degree multiple.

CORRECTION (2026-09-18). An earlier revision of this file claimed the best of the
four equivalent grasps could need almost 90 degrees and that a 45 degree
allowance would refuse stackable pairs. That was wrong, and the claim has been
withdrawn. The measurement behind it modelled the source candidates without
wrapping them into [-pi, pi), which is not what the code does:
`graspCandidates()` wraps every candidate with
  candidate_yaw = atan2(sin(raw_yaw), cos(raw_yaw))

With wrapped candidates the four reduced rotations are an arithmetic progression
with spacing exactly one symmetry step, so the nearest one is never further than
half a step from the requested placement rotation. The bound is therefore:

  best of the four equivalent grasps : <= half a symmetry step = <= 45 degrees
  chosen equivalent                  : <= the same 45 degrees

Re-measured over a full grid of source and destination yaws, wrapped candidates:
  worst best-of-four = 0.7831853072 rad (44.8732 degrees)
  worst any-of-four  = 0.7831853072 rad (44.8732 degrees)
i.e. 45 degrees is a tight upper bound, and 45 degrees is enough.

`maximum_stack_placement_rotation_rad` is configured to 0.7853981633974483
(45 degrees), the exact worst case the reduction can leave, so no reachable pair
is refused for want of a larger limit. Candidates above it are dropped before any
trajectory planning and recorded as `grasp_candidate_rejected`; if all four are
dropped the task fails while the arm is still at home.

Startup guard fix (2026-09-18)
------------------------------
The guard that refuses a too-small allowance compared it against
`target_yaw_symmetry_rad`, the configured fallback. That fallback is documented
as applying only when `use_target_size=false`; with measured sizes the locked
step comes from the detected top shape, and a square top uses half a turn of
symmetry steps. The guard was therefore twice as strict as run time and aborted
the node on the shipped 45 degree configuration:

  [FATAL] [fr3c_first_grasp]: P5 configuration/startup rejected:
  maximum_stack_placement_rotation_rad must allow at least half one
  yaw-symmetry step, otherwise rotating a cube onto the same yaw would always
  be refused

Because this validation runs in the constructor, before any
`rclcpp_action::create_server` call, the process exited with no action server
advertised at all. The client then blocked forever on
"Waiting for an action server to become available...", which is what the operator
observed; the arm correctly never moved because no goal was ever delivered.

The guard now compares against the smallest step that can occur at run time:
  const double symmetry = std::min(target_yaw_symmetry_rad_, kPi * 0.5);
and its message reports the threshold it computed. Verified against the shipped
configuration:

  old threshold 0.5 * 3.141592653589793 = 1.5707963267948966  -> abort
  new threshold 0.5 * min(pi, pi/2)     = 0.7853981633974483  -> pass
  limit 0.70 refused, 0.7853981633974483 accepted
  0.90 and 1.5707963267948966 accepted

All other startup numeric guards were re-checked against the shipped
configuration and pass, so this was the only blocker.

Cleanup guard fix (2026-09-18, second failure)
----------------------------------------------
First live attempt after the startup-guard fix reached the node and aborted with

  phase: retryable_failure_before_arm_motion
  error_code: 6 (PRECONDITION_FAILED)
  message: failed to remove the previous trial's world cube
  executed: false

No arm motion occurred, which is the intended fail-closed behavior; the bug was
in the precondition, not in the motion chain.

Cause. `clearPreviousCubeScene()` sent a world REMOVE unconditionally, but MoveIt
treats removing an object that is not present as a FAILURE, not as a no-op:

  PlanningScene::processCollisionObjectRemove()      (moveit_core/planning_scene)
    if (!world_->removeObject(object.id)) {
      RCLCPP_WARN_STREAM(LOGGER, "Tried to remove world object '" << object.id
                         << "', but it does not exist in this scene.");
      return false;
    }

which propagates PlanningSceneMonitor::newPlanningSceneMessage ->
ApplyPlanningScene.success=false -> PlanningSceneInterface::applyCollisionObject()
-> false. move_group's log confirms it received the request and refused it:

  [WARN] [moveit_planning_scene.planning_scene]: Tried to remove world object
  'target_cube', but it does not exist in this scene.

The live scene really was empty (verified with /get_planning_scene: no
target_cube, no stack_support_cube, no rviz_ground_plane). An empty scene is the
normal state before the first task of a freshly started stack, so the cleanup
meant to protect against leftovers refused the first legitimate task.

Fix. `clearPreviousCubeScene()` now checks existence first and returns success
when the cube is already absent, recording `previous_cube_absent`:

  if (planning_scene_.getObjects({cube_id_}).count(cube_id_) == 0) {
    recordEvent("previous_cube_absent", "world_id=" + cube_id_);
    return true;
  }

The same hazard was audited in the other cleanup paths and is already handled
there: `clearStackSupportObject()` returns early when the support obstacle is
absent, and `archivePreviousSortedCubeScene()` only removes the active cube
inside `if (previous.count(cube_id_) != 0)`. A regression test
(`test_clearing_an_absent_cube_is_a_no_op_not_a_failure`) now pins all three.

Verification: fairino_mtc_demo rebuilt cleanly; test_stack_task.py 12 passed;
full workspace regression 247 passed, 4 skipped.

Note on the node-scoped service. `PlanningSceneInterface` calls
`rclcpp::spin_until_future_complete()` on the same node that the
MultiThreadedExecutor is spinning, which is safe here only because the action
runs on its own worker thread. The function also has no explicit timeout, so a
lost response blocks rather than fails. Neither was the cause of this abort (the
call returned a definite false), but both are worth knowing if a future task
appears to hang in a planning-scene precondition.
